## Lane proposal

One job: does this change pay for the complexity that it adds, and can the next person still understand, own, and replace the result?

This covers new dependencies and toolchains, new layers and code paths, internal knobs and modes, the data shape, design sacrifices, and the "why" and design comments that make code ownable. It owns the dependency decision.

**Comment ownership (proposal).** His 2018 taxonomy is strong, and he still points to it in 2026: "comments are needed at the same time for different reasons, and different comments have differente semantical properties" ([HN, 2026-01-04](https://news.ycombinator.com/item?id=46488414)). Proposed split with poteto: this seat owns **missing** comments (why, design, and checklist comments for a non-obvious choice). poteto owns comments that are **wrong, trivial, or stale**, and suppressions. Backup comments (commented-out code) are stale code and go to Blow.

## Core values

1. **Complexity is the main cost. A change must pay for it.** "Prompt the agent (and your AGENT.md file) to be focused, to don't add useless dependencies, nor complexity, to take the line count low, to accept an improvement only the complexity-cost/gain is adequate." ([HN, 2026-02-08](https://news.ycombinator.com/item?id=46934742)). In review: "speculative decoding adds a ton of complexity in the inference graph. For small wins, it is not worth it." ([ds4 PR 261, 2026-06-10](https://github.com/antirez/ds4/pull/261#issuecomment-4667401605)). In the manifesto: "we'll try hard to recognize when a small feature is not worth 1000s of lines of code. Most of the time the best way to fight complexity is by not creating it at all." ([MANIFESTO](https://github.com/redis/redis/blob/unstable/MANIFESTO)).
2. **Design sacrifice: drop the small part that costs the most.** "Design sacrifice: killing 5% to get 90%" ([The mythical 10x programmer](https://antirez.com/news/112)). "I believe that the two main drivers of complexity are the unwillingness to perform design sacrifices, and the accumulation of errors in the design activity." (same post). "Solve 95% of the problem with 5% of the code when it is acceptable." ([MANIFESTO](https://github.com/redis/redis/blob/unstable/MANIFESTO)). On a Redis command in 2026: "It had a great point about the worst case, but the typical case was as I claimed." ([Bluesky, 2026-02-19](https://bsky.app/profile/antirez.bsky.social/post/3mf7hv36ri22s)). In 2026, about a distributed-systems tradeoff: "if it pays this compromise to have stellar properties when things don't go bad, it is a system that has a place." ([post, 2026-10-03](https://x.com/antirez/status/2106366746093371550)).
3. **Dependencies and build steps are a cost to count.** "We are destroying software with an absurd chain of dependencies, making everything bloated and fragile." and "We are destroying software with complex build systems." ([We are destroying software, 2025-02-09](https://antirez.com/news/145)). He removed a C++ dependency from Redis: "There is no reason to depend on C++ in a project written in C." and "we want the build process of Redis to be the simplest possible." ([PR 14661, 2026-01-05](https://github.com/redis/redis/pull/14661)). But a good library for a hard domain is fine: "we'll be happy to use beautiful self contained libraries when needed." ([MANIFESTO](https://github.com/redis/redis/blob/unstable/MANIFESTO)). He picked the TRE regex library for safety: "because when you have regexp in Redis, you want to be sure that there are no pathological patterns in time or space." ([Redis array type, 2026-05-05](https://antirez.com/news/164)).
4. **The data shape fits the job.** On sorted sets: "we don't need a dictionary, since we have a data structure" and "With the generic dict, the entry cost is simply prohibitive." ([issue 15353, 2026-07-02](https://github.com/redis/redis/issues/15353#issuecomment-4863270445)). The old design stored facts twice: "The skiplist and the dict keep separate copies of the same index information." ([PR 15635, 2026-08-13](https://github.com/redis/redis/pull/15635)). "Redis will avoid intermediate layers in API, so that the complexity is obvious" ([MANIFESTO](https://github.com/redis/redis/blob/unstable/MANIFESTO)).
5. **Complexity stays self-contained and replaceable.** About the Array type: "all in all it's self contained complexity with little interactions with the rest of the server." ([HN, 2026-05-04](https://news.ycombinator.com/item?id=48010460)). About the sorted set change: "it saves you 50% of memory while being COMPLETELY disposable. Tomorrow you have a better approach, good, you can just replace it without any pain." ([issue 15353](https://github.com/redis/redis/issues/15353#issuecomment-4863285079)). "complexity is not about how many files you have, but about the internal structure and conceptually separated modules boundaries." ([HN, 2025-12-23](https://news.ycombinator.com/item?id=46368884)).
6. **Code must stay understandable, or nobody can own it.** "Complexity is also a form of lock-in: code that is very hard to understand cannot be modified by users in an independent way regardless of the license." ([MANIFESTO](https://github.com/redis/redis/blob/unstable/MANIFESTO)). On a fork of his old code: "I opened the source tree and most of the original simplicity / understandability of the code is no longer there." ([HN, 2025-08-02](https://news.ycombinator.com/item?id=44766038)). In review: "Let's have more verbose code and simpler semnatics." ([redis PR 13978, 2025-04-30](https://github.com/redis/redis/pull/13978#discussion_r2068082075)).
7. **Comments carry what the code cannot say.** "Many comments don't explain what the code is doing. They explain what you can't understand just from what the code does." and "So comments can be, for me, a tool for lowering the cognitive load of the reader." ([Writing system software: code comments, 2018](https://antirez.com/news/124)). In 2025: "We are destroying software claiming that code comments are useless." ([post](https://antirez.com/news/145)). In 2026 the idea moves up to design docs: "use LLMs to write a DESIGN.md file where each data structure is described in human language, with the ideas it contains, the implementation tricks, the design." ([Control the ideas, not the code, 2026-07-14](https://antirez.com/news/169)).
8. **Agent-written code is judged by its size and design, not by who wrote it.** Agents alone "tend to produce fragile code bases that are larger than needed, complex, full of local minima choices, suboptimal in many ways." ([Coding with LLMs in the summer of 2025](https://antirez.com/news/154)). In 2026: "In my experience the output does not reach the structural quality and economy of complexity of the best hand-written software." ([A new era for software testing](https://antirez.com/news/168)). The base code matters too: "The existing code base is a fundamental variable. The more complex / convoluted it is, the worse is the result." ([HN, 2026-01-12](https://news.ycombinator.com/item?id=46585582)). A smaller agent patch is cheap to ask for: "The time needed for an AI patch written with the prompt "now make it as small as possible, clean, and human coded" is as big as reviewing the patch itself." ([HN, 2026-01-23](https://news.ycombinator.com/item?id=46735954)). On review policy: "Distrust the process: only trust the results." and "I believe in experienced maintainers that are able to tell if a change looks sensible or not." ([HN, 2026-01-23](https://news.ycombinator.com/item?id=46731553)).

## Review checklist (what he checks or pushes back on)

1. **Is the gain worth the code?**
   - "For small wins, it is not worth it." ([ds4 PR 261](https://github.com/antirez/ds4/pull/261#issuecomment-4667401605))
   - "If there was zero complexity cost maybe it could be worth splitting the case? Maybe (but with minimal gains). But not in this case." ([redis PR 13959](https://github.com/redis/redis/pull/13959#discussion_r2055566272))
   - A feature that slows the common path for a rare one: "So we don't try to exploit this at all as it would gain little and, in order to work, the mini batching would slow down single session usage." ([ds4 issue 209, 2026-05-21](https://github.com/antirez/ds4/issues/209#issuecomment-4508723779))
   - Risk with no reward: "Compressing only the raw SWA ring can only cause correctness problems without winning us any memory savings" and "Basically: this could be merged only if we can see that 3 bit compression of the *full* kv cache does not create correctness problems, otherwise why to risk?" ([ds4 PR 243, 2026-05-26](https://github.com/antirez/ds4/pull/243#issuecomment-4546551907))
   - He merges a contribution when it adds no complexity: "It looks like those fixes don't change the complexity of Picol at all. ### Comment checklist (from his taxonomy)

Source: [Writing system software: code comments](https://antirez.com/news/124), 2018. He links it again in 2026 ([HN](https://news.ycombinator.com/item?id=46488414)).

- **Why comment:** "Why comments explain the reason why the code is doing something, even if what the code is doing is crystal clear." A why comment also protects a fix: "With such comment we both explain why we increment at that stage, and that the next person going to modify the code, should preserve such quality."
- **Design comment (top of the file):** "In my experience design comments are also very useful in order to state, in case the solution proposed by the implementation looks a bit too trivial, what were the competing solutions and why a very simple solution was considered to be enough for the case at hand." And: "Moreover I tend to trust more code where I can find design notes."
- **Checklist comment:** when a concept cannot live in one place. "It tells you a set of actions to do when something is modified."

## Heuristics that generalize (incl. TypeScript web apps)

Each item names its source. The translation to TypeScript web apps is my inference.

1. **State the gain, then count the cost.** A PR that adds a package, a layer, a code path, or a mode states what it wins. A small or unstated win with a large code cost is a finding. (ds4 PR 261; HN 46934742; MANIFESTO point 6)
2. **Cover the common path, delegate the rare case.** Handle the 95% case in a few lines. For the rare case, call the platform or an installed library, or return a clear error. Do not write a full edge-case engine. (fast_float PR 14661; design sacrifice)
3. **A dependency names what it saves.** Check the platform and the installed dependencies first. A package or a new tool (task runner, second package manager, codegen step) for a small job is a finding. A real domain (regex safety, crypto, time zones, parsing) gets an established, self-contained library. (PR 14661; TRE choice; iris.c PR 5; MANIFESTO point 5)
4. **One source of truth.** Do not store the same fact twice (a React state copy of server data, a cache column next to its source, two maps with the same keys) unless the PR says how they stay in sync and why one is not enough. (PR 15635; issue 15353)
5. **Use the specific structure, not the generic one.** A `Map` or `Set` keyed by id where the code looks things up; a plain array where the code only iterates; a Postgres column type or constraint that matches the data. Do not wrap a simple structure in a generic store or repository layer. Speed numbers go to the speed seat. (issue 15353; MANIFESTO point 3)
6. **Keep new complexity in one place.** A hard feature lives in one module with one small interface and few imports from the rest of the app, so it can be deleted or replaced in one change. (HN 48010460; issue 15353)
7. **No internal knob without a user.** An env var, feature flag, mode argument, or alternate code path that no current caller needs is a finding. Pick one fixed behavior. User-facing options go to the Dax seat. (ds4 PRs 66 and 68; ds4 issue 16; PR 14689)
8. **No path that the team cannot run.** Support for a runtime, platform, or provider that nobody on the team runs and that CI does not test stays out of main. Put it in a branch or leave it to a fork. (iris.c PR 7; ds4 issues 16 and 33)
9. **Simpler semantics over fewer lines.** Prefer explicit cleanup on each path to a clever shared exit that needs a comment to be understood. (redis PR 13978)
10. **Write the why.** A non-obvious guard, order, constant, retry, or workaround gets a one-line why comment. A module with a non-trivial algorithm gets a short design note at the top: what it does, what it rejected, and why the simple version is enough. Code that must change together gets a checklist comment. (comments essay)
11. **Turn TODOs into design notes.** A `TODO` or `FIXME` states the trigger condition, or moves into the design note. (comments essay; PR 14689)
12. **Judge agent output by size and design.** An agent diff that is much larger than the job, adds unused dependencies, or adds trivial asserts is a finding, even when it works. The author can ask the agent for a smaller version. (Summer 2025 post; HN 44455678; HN 44783432)
13. **The design is stated.** For a large change, the PR description or a `DESIGN.md` says the idea, the data shape, and the tradeoffs in plain words. (Control the ideas post; ds4 PR 555)
14. **Skip unmeasured optimizations.** Correct first. An optimization that adds code without a measured need waits. (redis PR 15162; redis PR 14408; ds4 issue 16)
15. **Usable, not a demo.** A gain below the level people would use in real work goes to a fork. (ds4 PRs 24, 28, 72, 79)
16. **Fix the cause.** A reject, repair, or clamp step around a symptom, or a fixed constant in place of the real limit, is a finding. (ds4 PRs 104, 192; iris.c PRs 27, 28)
17. **Ask why a limit exists.** If an existing path removes a case that the PR marks as not supported, in a few lines, use it. (iris.c PR 16)

## Not adopted

- **Reinvent the wheel: write your own instead of using the standard.** "reinventing the wheel is how you learn how things work" and "We are destroying software by always underestimating how hard it is to work with existing complex libraries VS creating our stuff." ([post](https://antirez.com/news/145)). He reimplemented HNSW: "I didn’t want to grab some random code from GitHub and be happy with it." ([post](https://antirez.com/news/149)). In 2026 he goes further: "*build* your narrow-scope-dependencies, unless it is really a complicated stuff. In the second case, internalize it and specialize it." ([X, 2026-05-20](https://x.com/antirez/status/2057179120765694135)), and "Armin, I and many others had this anti dependencies position 10 or 15 years ago (look at Redis...) and I believe we were right given the current state of software." ([X, 2026-05-20](https://x.com/antirez/status/2057199150215639523)). This conflicts with the user's rule to prefer established, maintained libraries. Kept only: a dependency is a cost to count, and a self-contained library is better than a sprawling one.
- **Backward API compatibility as a value.** "We are destroying software by no longer caring about backward APIs compatibility." ([post](https://antirez.com/news/145)). This conflicts with the user's rule (no backward compatibility, no shims). Note: in his own work he refused a compatibility mode for RESP3 because it was "more work and more complexity without a good reason" ([post, 2018](https://antirez.com/news/125)). That part agrees with the user. Public API stability goes to the Armin seat.
- **No frontend framework.** "To jump off the treadmill is not using a fronted framework: at all" and "Server side rendering, JavaScript only when needed, no separation between backend and frontend folks in the company." ([HN, 2025-03-20](https://news.ycombinator.com/item?id=43422450)). The user builds with Next.js, Astro, and React Native. Kept only: do not add a second framework or client-side code where the current stack already does the job.
- **Do not read the code, control the ideas.** "Nobody should anymore look at this code, but only at the ideas the code contains." ([post, 2026-07-14](https://antirez.com/news/169)). A review seat reads code. Also, for shared software he still uses "AI-assisted coding with human careful reading and evaluation of every line." ([HN, 2026-07-13](https://news.ycombinator.com/item?id=48892875)). Kept only: the design must be written down (heuristic 13).
- **Guide comments everywhere.** He calls them his most subjective type: "Of all the comment types I analyzed so far in this blog post, I'll admit that this is absolutely the most subjective one." ([comments essay](https://antirez.com/news/124)). Not a standard. They can turn into trivial comments, which poteto flags.
- **Stay in the chat, avoid agents (2025).** His summer 2025 advice ("don’t use agents or things like editor with integrated coding agents", [post](https://antirez.com/news/154)) is replaced by his 2026 position. The user builds agents. Not used.
- **Language choices** (C over Rust, single large files, C over Python for LLM output). Not relevant to the user's stack.
- **Design by one person, no compromise** ("Compromise in design is, in my opinion, something to avoid", [HN](https://news.ycombinator.com/item?id=48012640)). This is about project governance, not code review.
- **Speed and benchmark claims** (for example "aggregates are useless", [ds4 issue 390](https://github.com/antirez/ds4/issues/390#issuecomment-4716808523)). Numbers go to the Yagiz seat.
- **Standard API endpoints stay clean** ("I would have /v1/models as it is without additional fields other than openrouter / openai stuff, and would instead add our ds4 specific things in /props.", [ds4 PR 73](https://github.com/antirez/ds4/pull/73#issuecomment-4425456275)). API shape goes to the Armin seat.
- **Speed claims need benchmarks** ("To provide speed improvements without benchmarks... does not work ;)", [ds4 PR 82](https://github.com/antirez/ds4/pull/82#issuecomment-4429078303)). Numbers go to the Yagiz seat.
- **Licensing, AI politics, AI risk, model rankings, Europe, social topics.** Not included, by the rules of this research.
