# Daniel Stenberg (@bagder): code-review research

Research date: 2026-11-26. Weighting: 2025-11-26 to 2026-11-26 highest.
Main corpus: 574 of his inline PR review comments in 290 `curl/curl` PRs and 1,832 of his issue and PR conversation comments in 1,110 `curl/curl` threads, 2025-11-27 to 2026-11-25 (all `curl/curl` comments with `since=2025-11-26`, filtered on `user.login == bagder`). Search counts for the same window: 1,883 threads with `commenter:bagder`, 1,068 with `reviewed-by:bagder`, 177 outside `curl/curl`. Other sources: 67 of his blog posts from the window and 73 from earlier in 2025 (daniel.haxx.se, WordPress API), 2,400 of his Mastodon posts (2026-02-03 to 2026-11-25), two committed project documents that he maintains (`docs/VULN-DISCLOSURE-POLICY.md`, `docs/CONTRIBUTE.md`), and 7 PR review threads fetched in full for the replay test.
Every quote is verbatim. I kept his typos ("What the logic here?", "its not a vulnerability"). A script checked each quote against the fetched text. "Inference" marks my own reading.

**Agent-written text.** None of his own comments in the corpus says that an agent wrote it. He calls agent text "clanker" output and asks people to stop it. Where a quote replies to agent text, I say so.

**How he reviews.** Most inline comments are one or two sentences: a question ("Why?", "Right?", "When is that useful?") or a `suggestion` block with the exact fix. Since 2026-10-26 he also assesses public vulnerability reports in `curl/curl` issues, and those comments give a severity call with numbered reasons. That gives this seat more severity evidence than any other seat.

## Current focus (what he works on now)

- **An avalanche of AI-found vulnerability reports.** "The rate of incoming security reports is 4-5 times higher than it was in 2024 and double the speed of 2025 – meaning that on average we now get more than one report per day. The quality is way higher than ever before." ([The pressure, 2026-05-26](https://daniel.haxx.se/blog/2026/05/26/the-pressure/)). "Out of all #curl CVEs we have registered since 2019, 41% have been registered in 2026" ([Mastodon](https://mastodon.social/@bagder/117474053587482548)).
- **LOW and MEDIUM vulnerabilities in public.** "starting October 26 2026, we insist that all vulnerability reports submitted to us that are deemed to be severity LOW or MEDIUM should instead be submitted as issues in our GitHub repository." ([Do minor curl vulnerabilities in the open, 2026-10-20](https://daniel.haxx.se/blog/2026/10/20/do-minor-curl-vulnerabilities-in-the-open/)).
- **A higher bar for LOW.** "for those who follow: yeah, we're gradually raising the bar for what we accept as LOW severity #curl vulnerabilities." ([Mastodon](https://mastodon.social/@bagder/117591577273633706)). "Issues that seem too ridiculous or unlikely we now set to NONE to a larger extent than we have in the past." ([curl on OSS-Scanner, 2026-11-18](https://daniel.haxx.se/blog/2026/11/18/curl-on-oss-scanner/)).
- **The first HIGH since 2023: an HTTP/2 use-after-free.** "It is a use-after-free, which is a classic problem in memory-unsafe programming languages, like C, where we erroneously have a lingering pointer left, pointing to memory that is already freed, and yet we use that pointer and the memory it points to." ([A UAF turned RCE, 2026-10-14](https://daniel.haxx.se/blog/2026/10/14/a-uaf-turned-rce/)).
- **Banning hard-to-use C functions.** `strncpy`, `strcpy`, `atoi`, and `strtol` are gone from curl ([no strcpy either, 2025-12-29](https://daniel.haxx.se/blog/2025/12/29/no-strcpy-either/); [Parsing integers in C, 2025-11-13](https://daniel.haxx.se/blog/2025/11/13/parsing-integers-in-c/)).
- **Hostname edge cases.** Trailing dots, IDN confusables, and certificate name checks ([Trailing dots are the worst, 2026-06-25](https://daniel.haxx.se/blog/2026/06/25/trailing-dots-are-the-worst/); [openssl#33420](https://github.com/openssl/openssl/issues/33420#issuecomment-6911530876)).
- **Less complexity, fewer old protocols.** The worst function went from complexity 100 to 59 ([decomplexification continued, 2026-02-24](https://daniel.haxx.se/blog/2026/02/24/decomplexification-continued/)). NTLM and SMB became opt-in ([NTLM and SMB go opt-in, 2026-03-22](https://daniel.haxx.se/blog/2026/03/22/ntlm-and-smb-go-opt-in/)).

## Core values

1. **Parse strictly. Reject bad input. Do not guess.** "I think we in the curl project as well as more or less the entire world has learned through the years that it is usually better to be strict when parsing protocols and data, rather than be lenient and try to accept many things and guess what it otherwise maybe meant." and "For security and for solid functionality, providing syntactically incorrect data is not accepted." ([Parsing integers in C](https://daniel.haxx.se/blog/2025/11/13/parsing-integers-in-c/)). In review: "I don't think we should go with this \"leniency\". If the server responds with this syntactical problem I think it is better to bail out with the same control-code error." ([curl#20949](https://github.com/curl/curl/pull/20949#discussion_r2946071039)).
2. **Every input has a limit.** "they do not accept strings longer than a set limit. We deem that any string set that is longer is either just a blatant mistake or some kind of attempt (attack?) to trigger something weird inside the library." and "Each dynamic buffer also has its own maximum size set, which in its simplicity also helps catching mistakes." ([Writing C for curl, 2025-04-07](https://daniel.haxx.se/blog/2025/04/07/writing-c-for-curl/)). On numbers: "It also has a max value argument so that it returns error if too large." ([Parsing integers in C](https://daniel.haxx.se/blog/2025/11/13/parsing-integers-in-c/)).
3. **Keep the check next to the operation.** "Over time however – let’s imagine we have code that lives on for decades – when code is maintained, patched, improved and polished by many different authors with different mindsets and approaches, those size checks and the function invoke may glide apart." and "To make sure that the size checks cannot be separated from the copy itself we introduced a string copy replacement function" ([no strcpy either](https://daniel.haxx.se/blog/2025/12/29/no-strcpy-either/)).
4. **A bug is not a vulnerability.** "For every report we work hard to first assess and decide if the issue is actually a vulnerability or a security problem at all." and "Every CVE thus has this huge cost tied to it." ([a CVE dispute, 2026-06-24](https://daniel.haxx.se/blog/2026/06/24/a-cve-dispute/)). "The AIs are also still bad at figuring out exactly where the line is between a bug and a vulnerability, and if it is a vulnerability, what severity it is." ([“ignore the slop”, 2026-10-22](https://daniel.haxx.se/blog/2026/10/22/ignore-the-slop/)).
5. **Real vulnerabilities are never ignored.** "Ignoring real vulnerabilities because they were found by AI does not make users safe and secure. It makes them vulnerable." ([“ignore the slop”](https://daniel.haxx.se/blog/2026/10/22/ignore-the-slop/)). "Security problems never linger around once they have been reported." ([Don’t trust, verify, 2026-03-26](https://daniel.haxx.se/blog/2026/03/26/dont-trust-verify/)).
6. **Verify, do not trust.** "Software and digital security should rely on verification, rather than trust." ([Don’t trust, verify](https://daniel.haxx.se/blog/2026/03/26/dont-trust-verify/)).
7. **Humans own every merge. Tools help.** "We stand for every bit of code we merge – as humans." and "curl is developed and driven by humans, assisted by tools." ([A human in control, 2026-06-10](https://daniel.haxx.se/blog/2026/06/10/a-human-in-control/)). "Humans must always drive the process, taking full responsibility for presenting, reviewing, and understanding every change." ([Mastodon](https://mastodon.social/@bagder/116679352280628139)).
8. **C is not memory-safe, and he counts it.** "Out of the 81 vulnerabilities we have confirmed in #curl so far during 2026, 14 were the result of mistakes that most likely would have been avoided had we used a memory-safe language such as rust. That's 17.3%" ([Mastodon](https://mastodon.social/@bagder/117628704524069340)). The classes: "OVERFLOW, OVERREAD, DOUBLE_FREE, USE_AFTER_FREE, NULL_MISTAKE, UNINIT and BAD_FREE" ([Mastodon](https://mastodon.social/@bagder/117239576303445248)).

## Review checklist (what he checks or pushes back on)

1. **Does the parser match more than it should?**
   - A length-based compare: "since you're using the length as provided, this logic will also match with `pr` and any other substring of \"pretty\", which I think it shouldn't" ([curl#22295](https://github.com/curl/curl/pull/22295#discussion_r3669404567)).
   - A netrc keyword match: "won't this (and the following checks) also match `machin` etc because of its prefix-checking nature based on length `slen`?" ([curl#21624](https://github.com/curl/curl/pull/21624#discussion_r3248038468)).
   - Control bytes in a decoded field: "I suggest we are more restrictive. No alpn code has control code or null bytes" ([curl#23657](https://github.com/curl/curl/pull/23657#discussion_r4410138046)).
   - An encoded bracket: "the parser previously did not accept `%5b` as a `[` replacement when parsing IPv6 either. And it should not." (his own PR, reply to a review remark, [curl#22924](https://github.com/curl/curl/pull/22924#discussion_r3996917539)).
2. **Too long: fail, do not truncate.** "Since libcurl allows longer hostnames, maybe a check here should rather fail if the name is too long rather than just silently truncate here?" ([curl#21874](https://github.com/curl/curl/pull/21874#discussion_r3363250897)). "maybe make this limit even smaller to detect abuse/mistakes better? Surely this should never be larger than CURL_MAX_INPUT_LENGTH or so?" ([curl#21840](https://github.com/curl/curl/pull/21840#discussion_r3339470450)).
3. **Is every arithmetic operation safe from overflow?** "Every arithmetic operation done needs to be done with a certainty that it does not overflow. This is unfortunately still mostly a manual labor, left for human reviews to detect." ([Writing C for curl](https://daniel.haxx.se/blog/2025/04/07/writing-c-for-curl/)). A size that goes wrong: "Since skipping this increment makes the size wrong, shouldn't this rather error if it actually reaches this point?" ([curl#23604](https://github.com/curl/curl/pull/23604#discussion_r4375439505)). A user value that overflows: "One way to avoid this could be to cap the maximum timeout value to something sensible." ([curl#21782](https://github.com/curl/curl/issues/21782#issuecomment-4558399659)).
4. **Does the change remove a guard?** "You introduced that risk yourself by removing the guards we have in place to make sure that risk doesn't exist in curl." ([curl#22228](https://github.com/curl/curl/issues/22228#issuecomment-4847953919)). On a removed check: "Are you **100%** sure those claims are incorrect?" and "To me, it seems safer to keep the check." ([curl#23426](https://github.com/curl/curl/pull/23426#discussion_r4291865853)).
5. **Can a pointer outlive what it points to?** "The 429 list may live longer than the individual transfers so the origin pointers might then point to freed memory. Won't they?" ([curl#21355 review](https://github.com/curl/curl/pull/21355#pullrequestreview-4404912516)). The structural fix: "we store transfer identifiers that we look-up on demand. While this is a tiny bit slower, it is more foolproof when there are logical mistakes like the one mentioned here." ([A UAF turned RCE](https://daniel.haxx.se/blog/2026/10/14/a-uaf-turned-rce/)).
6. **Is each fallible call checked, on each path?** "This function is fallible, like in low memory situations. You need to check that you actually get a hostname back." ([curl#21355](https://github.com/curl/curl/pull/21355#discussion_r3108614248)). "If the urldecode above failed, I think this one should be avoided." ([curl#21710](https://github.com/curl/curl/pull/21710#discussion_r3286889055)). "In curl we always check for errors and we bail out without leaking any memory if (when!) they happen." ([Writing C for curl](https://daniel.haxx.se/blog/2025/04/07/writing-c-for-curl/)).
7. **Does it copy a helper that already exists?** "Maybe this is a reason to just use `Curl_urldecode()` instead of duplicating this code and accept that it allocates the new string?" ([curl#23657](https://github.com/curl/curl/pull/23657#discussion_r4406517167)). "We have `curlx_hexval()` for exactly this already I believe." ([curl#23657](https://github.com/curl/curl/pull/23657#discussion_r4406489046)). "We prefer avoiding \"raw\" allocs + fiddling and rather use functions that handle it themselves." ([curl#21355](https://github.com/curl/curl/pull/21355#discussion_r3511161323)).
8. **Is the check hidden?** "Isn't it better to have the checks in the curlx_* functions rather than \"hiding\" them in macros like this? I know I certainly much prefer that. macros like this are hard to spot and they are hard to see in a debugger etc." ([curl#21645](https://github.com/curl/curl/pull/21645#discussion_r3253647453)). For internal callers: "This is an internal function that should *never* be called with bad parameters. I think they are better checked with DEBUGASSERT()s" ([curl#23062](https://github.com/curl/curl/pull/23062#discussion_r4087624680)).
9. **What does this protect against?** On a PR that strips `Proxy-Authorization` on redirect: "`Proxy-Authorization` is not really related to the origin, it is for a proxy and a proxy is presumably going to be the same when you follow a redirect so why would it drop this header just because of this?" and "What is this protecting against? Who wants this and why?" ([curl#21578](https://github.com/curl/curl/pull/21578#discussion_r3232519435)). On a TLS session key change: "Can you show us an example of a configuration mismatch that is fixed by adding the lengths like this?" ([curl#23357](https://github.com/curl/curl/pull/23357#issuecomment-6141934064)).
10. **Credentials and connection reuse.** "We can't know if the user that isn't known, might be a different one in the second transfer. So to play it safe, we have to deny reuse." ([curl#22528](https://github.com/curl/curl/pull/22528#issuecomment-5268799681)). He links the past case: "Related: [CVE-2025-14524: bearer token leak on cross-protocol redirect]" ([curl#23796](https://github.com/curl/curl/issues/23796#issuecomment-6706613961)). A CA store change: "Shouldn't it require a recheck?" ([curl#23495](https://github.com/curl/curl/issues/23495#issuecomment-6272307639)).
11. **TLS verification stays on.** "Skipping the certificate verification makes the connection insecure." and "In almost all cases, you can fix the failed verification the proper way instead of disabling the check. It is just usually a little more work." ([disabling cert checks: we have not learned much, 2025-02-11](https://daniel.haxx.se/blog/2025/02/11/disabling-cert-checks-we-have-not-learned-much/)). A library change that weakens it: "This is a regression and a security flaw introduced in 4.1 that weakens certificate checks by applications using OpenSSL. You can't fix this with documentation." ([openssl#33420](https://github.com/openssl/openssl/issues/33420#issuecomment-6911530876)).
12. **Normalize the hostname before the security decision.** The IP check: "it needs to know if the given hostname is a numerical IP or a hostname. The check uses inet_pton() on the provided hostname extracted from the URL – which incidentally returns false for an IPv4 address that ends with dot!" The cookie check: "Turns out this too could be tricked by trailing dots." ([Trailing dots are the worst](https://daniel.haxx.se/blog/2026/06/25/trailing-dots-are-the-worst/)). IDN: "if you pass \"trusted.example＠evil.example\" into an IDN decoder, you get \"trusted.example@evil.example\" out from it." ([Mastodon](https://mastodon.social/@bagder/117480932553766809)).
13. **Does the test prove the fix?** "This URL does not contain any credentials. Doesn't that make this test succeed even without this patch?" ([curl#23020](https://github.com/curl/curl/pull/23020#discussion_r4062616900)). He asks for edge values: "ranges that end of the largest possible (2^63-1) number" ([curl#23236](https://github.com/curl/curl/pull/23236#discussion_r4302902023)) and "Won't it make sense to verify the exact border time stamp on both sides of the capped point?" ([curl#21494](https://github.com/curl/curl/pull/21494#discussion_r3199196898)).
14. **Is the fix simple and in the right place?** "I think this solution is far too complicated and I dislike the sloppy-generated huge comments. Please apply more human brains on your work. I think the function that parses the incoming Digest header should rather discount it as an auth alternative for this response if it uses an algorithm that curl doesn't support." ([curl#23698](https://github.com/curl/curl/pull/23698#issuecomment-6580745585)). "I don't think we need this rather complicated fix. curl has done without it for decades and provide and document several ways to avoid getting credentials in the process list if people care." ([curl#22733](https://github.com/curl/curl/pull/22733#issuecomment-6361199691)).
15. **Should broken, risky code just go?** "We have received reports about suspected security problems in this part of the code and I think instead of spending time on fixing something that is known to be broken already, it feels better to just decide that we put an end to it." ([curl#22703](https://github.com/curl/curl/issues/22703#issuecomment-5445533455)). NTLM: "curl has recorded no less than seven past security vulnerabilities in NTLM related code!" ([NTLM and SMB go opt-in](https://daniel.haxx.se/blog/2026/03/22/ntlm-and-smb-go-opt-in/)).

### Severity calls (how he scores a finding)

From the policy that he maintains (last commit by him 2026-10-19, [VULN-DISCLOSURE-POLICY.md](https://github.com/curl/curl/blob/c190227d91/docs/VULN-DISCLOSURE-POLICY.md)):
- "we take all the factors into account: attack vector, attack complexity, required privileges, necessary build configuration, protocols involved, platform specifics and also what effects a possible exploit or trigger of the issue can lead to, including confidentiality, integrity or availability problems."
- LOW: "This is a security problem that is truly hard or unlikely to exploit or trigger." and "Issues that are likely to be detected by basic testing are likely to not be considered more severe than **Low**."
- HIGH: "Flaws that can easily compromise the confidentiality, integrity or availability of resources. Exploiting or triggering this problem is not hard."
- CRITICAL: "Easily exploitable by a remote unauthenticated attacker and lead to system compromise (arbitrary code execution) without requiring user interaction, with a common configuration on a popular platform."
- API misuse: "If a reported issue only triggers by an application using the API in a way that is not documented to work or even documented to not work, it is probably not going to be considered a security problem."
- Local attackers: "When an issue can only be attacked or misused by an attacker present on the local system or network, the bar is raised."
- Crashes: "If a malicious server can trigger a NULL dereference in curl or otherwise cause curl to crash (and nothing worse), chances are big that we do not consider that a security problem."
- Leaks: "We do not consider a small memory leak a security problem" and "If leaked memory contains sensitive data it might also qualify as a security problem."
- CRLF: "curl makes barely any claims of *cleaning* input or rejecting invalid data."

His calls in the last month (public `vuln:ASSESS` issues):
- Needs an attacker: "While a UAF, I don't think we need to treat this as a vulnerability." with "this problem cannot reasonably be triggered by an attacker" ([curl#23629](https://github.com/curl/curl/issues/23629#issuecomment-6442226142)). "The problem does cause a read outside of its buffer, but it is not attacker controlled." ([curl#23712](https://github.com/curl/curl/issues/23712#issuecomment-6582268915)).
- Found by the first test: "Anyone testing this combination will *immediately* realize it doesn't work so it seems unlikely that users would unknowingly do this in production" ([curl#23783](https://github.com/curl/curl/issues/23783#issuecomment-6687882023)). "It's not likely to ship and hurt unknowing users. And an attacker cannot exploit it. Let's call it a bug." ([curl#23803](https://github.com/curl/curl/issues/23803#issuecomment-6720647343)).
- Documented behavior: "No. This is documented behavior, so its not a vulnerability at all. You propose modified behavior." ([curl#24142](https://github.com/curl/curl/pull/24142#issuecomment-7155209288)). "They're not *injected*, the user selects to pass them there." ([curl#23798](https://github.com/curl/curl/issues/23798#issuecomment-6705393492)).
- A chain of unlikely steps: "It's like a sequence of highly unlikely steps that need to happen." ([curl#23699](https://github.com/curl/curl/issues/23699#issuecomment-6579906313)).
- Fails cleanly: "curl still fails correctly if it runs out of memory in this process and it exists cleanly, with not leaks and no disclosures." ([curl#23829](https://github.com/curl/curl/issues/23829#issuecomment-6737722583)).
- Still a vulnerability: "Since this is an actual UAF problem when using the API as documented, it seems reasonable to consider this a vulnerability." ([curl#23785](https://github.com/curl/curl/issues/23785#issuecomment-6705833461)). On a pinning bypass that also happens with `-k`: "I think we should consider this a vulnerability and MEDIUM seems suitable." ([curl#23755](https://github.com/curl/curl/issues/23755#issuecomment-6681197206)).
- Asks for harm: "I would like to see a plausible situation described how this can cause real harm to consider this a vulnerability." ([curl#24091](https://github.com/curl/curl/issues/24091#issuecomment-7081413441)).
- Defense in depth is not the same as a vulnerability: "We can argue that we should do defense in-depth here and not reuse the connection for this case, but the *vulnerability* if any is not curl's I think." ([curl#23833](https://github.com/curl/curl/issues/23833#issuecomment-6795805434)).

## Hard "no"s / pet peeves

- Leniency in parsers, and guessing what bad input meant ([Parsing integers in C](https://daniel.haxx.se/blog/2025/11/13/parsing-integers-in-c/), [curl#20949](https://github.com/curl/curl/pull/20949#discussion_r2946071039)).
- Functions he bans: "gets, sprintf, strcat, strtok, localtime, etc" and "We avoid sscanf and strncpy for those reasons." ([Writing C for curl](https://daniel.haxx.se/blog/2025/04/07/writing-c-for-curl/)). `atoi`: "they return 0 instead of an error, that they have no checks for under or overflow" ([Parsing integers in C](https://daniel.haxx.se/blog/2025/11/13/parsing-integers-in-c/)).
- Disabled certificate checks ([disabling cert checks](https://daniel.haxx.se/blog/2025/02/11/disabling-cert-checks-we-have-not-learned-much/)).
- Inflated severity: "Many of them overstate the problem. Many of them claim a vulnerability when its just a minor bug." ([Mastodon](https://mastodon.social/@bagder/117468007646824246)).
- Long AI text in human conversation: "Inserting a large AI generated tone-deaf large wall-of-text into such a flow can still work, but only in the same way humans can learn to work with difficult individuals as well." ([A human in control](https://daniel.haxx.se/blog/2026/06/10/a-human-in-control/)).
- Hidden or obfuscated content in the repository: "we ban use of “binary blobs” in git to not provide means for malicious actors to bundle encrypted payloads" and "we actively avoid base64 encoded chunks as they too could function as ways to obfuscate malicious contents" ([Don’t trust, verify](https://daniel.haxx.se/blog/2026/03/26/dont-trust-verify/)).
- Environment variables as an override for a safety filter: "Environment variables make for horrible APIs" ([Leeks and leaks, 2025-05-16](https://daniel.haxx.se/blog/2025/05/16/leeks-and-leaks/)).

## Heuristics that generalize (incl. TypeScript web apps)

1. **One strict parser per format, with a max.** Inference: in TypeScript, a `Number(x)`, `parseInt(x)`, or `+x` on request input is the `atoi` of the web. Use a schema with `int`, `min`, and `max`, and reject on failure. Match his `curlx_str_number()`: "This function of ours does not allow any leading whitespace and certainly no prefixing pluses or minuses." ([Parsing integers in C](https://daniel.haxx.se/blog/2025/11/13/parsing-integers-in-c/)).
2. **Exact compare, not a prefix or substring.** Inference: `startsWith`, `includes`, or `indexOf` on a host, origin, path, or keyword is the `machin` bug ([curl#21624](https://github.com/curl/curl/pull/21624#discussion_r3248038468)). Parse the URL and compare `url.hostname` and `url.origin` exactly.
3. **Normalize before you decide.** Inference: lower-case the host, strip one trailing dot, apply IDN to ASCII, and reject confusables before a cookie domain, allowlist, CORS origin, or SSRF check ([Trailing dots are the worst](https://daniel.haxx.se/blog/2026/06/25/trailing-dots-are-the-worst/)).
4. **Fail on too long. Never cut silently.** Inference: `.slice(0, n)` on a name, token, or path before a security check changes what you check ([curl#21874](https://github.com/curl/curl/pull/21874#discussion_r3363250897)).
5. **A credential follows its origin.** Inference: an `Authorization` header, cookie, or token goes only to the host and scheme it was for. On a redirect, `fetch` drops `Authorization` across origins; a hand-written redirect loop must do the same ([CVE-2025-14524 link](https://github.com/curl/curl/issues/23796#issuecomment-6706613961)). A proxy credential is not origin-bound ([curl#21578](https://github.com/curl/curl/pull/21578#discussion_r3232519435)).
6. **Ids over pointers for long-lived state.** Inference: a cache, map, or queue that outlives a request holds an id and looks up fresh state, not a captured object ([A UAF turned RCE](https://daniel.haxx.se/blog/2026/10/14/a-uaf-turned-rce/)).
7. **Severity by attacker, not by bug class.** Ask who controls the input, what they gain, and whether a basic test finds it first. A crash or leak that only the app's own wrong use can trigger is a bug ([VULN-DISCLOSURE-POLICY.md](https://github.com/curl/curl/blob/c190227d91/docs/VULN-DISCLOSURE-POLICY.md)).
8. **CI cannot write back.** "we make sure that the CI jobs we have for curl never “write back” to curl. They access the source repository read-only and even if they would be breached, they cannot infect or taint source code." and "we run zizmor and other code analyzer tools on the CI job config scripts to reduce the risk of us running or using insecure CI jobs." ([Don’t trust, verify](https://daniel.haxx.se/blog/2026/03/26/dont-trust-verify/)).
9. **Confusable characters in a diff are a finding.** "he replaced an ASCII letter with a Unicode alternative in a URL." and "We have added a CI job that scans all files and validates every UTF-8 sequence in the git repository." ([Detecting malicious Unicode, 2025-05-16](https://daniel.haxx.se/blog/2025/05/16/detecting-malicious-unicode/)).
10. **A dependency's security change is your security change.** "OpenSSL subtly changed an API function behavior so that curl now accepts a certificate that it shouldn't, using code that has worked with OpenSSL for decades." ([Mastodon](https://mastodon.social/@bagder/117651066432094546)). But old dependencies are the user's job: "The established remedy is to upgrade your OpenSSL to a fixed version." ([curl#23985](https://github.com/curl/curl/issues/23985#issuecomment-6909694223)).
11. **Verify AI claims both ways.** "You must also double-check the findings carefully before reporting them to us to validate that the issues are indeed existing and working exactly as the AI says." ([CONTRIBUTE.md](https://github.com/curl/curl/blob/7e1001bcd6/docs/CONTRIBUTE.md)). And do not delete a check only because an agent said so ([curl#23426](https://github.com/curl/curl/pull/23426#discussion_r4291865853)).

## Lane fit (for the seat)

The seat keeps the Troy lane: can an attacker or a leak get data or access that they must not get. Daniel's evidence covers input parsing, limits, integer overflow, memory lifetime, credentials on redirect and reuse, TLS verification, hostname normalization, supply chain and CI, and severity judgment. It does not cover web-app auth flows (RLS, account enumeration, reset tokens, passwords, passkeys, rate limits, bundle secrets, CSP, cookie flags, webhooks). Those stay as baseline checks with no Daniel source.

Handoffs: a leak on an error path with no attacker, OOM handling, and test design go to Mitchell (Daniel's own policy says a small leak is not a security problem). Error codes and messages go to Armin. Speed goes to Yagiz. The decision to add a dependency goes to antirez. Rust `unsafe` proofs go to burntsushi.
