## Core values

1. **One run, at the top.** "usage of `runSync` should be consider an exception and by all means not the norm, in a normal program you should have a single run at the top which is a `runMain` not a `runSync` so we can consider using async ops and then using `runSync` to be a code defect" ([effect#4291](https://github.com/Effect-TS/effect/issues/4291#issuecomment-2603600483)).
2. **No function coloring.** "Effect is a unified model of computation that doesn't require function coloring (that has know drawbacks)" ([effect#4291](https://github.com/Effect-TS/effect/issues/4291#issuecomment-2603600483)).
3. **Compose the dependency graph, then provide it once.** On a user snippet: "the snippet also shows some anti-patterns, namely leaking services on usage and multiple Effect.provide calls" ([effect#5202](https://github.com/Effect-TS/effect/issues/5202#issuecomment-3094379094)).
4. **Use the primitive that exists. Reject ad-hoc API.** "why not using plain Effect.timeout?" ([effect#4709](https://github.com/Effect-TS/effect/pull/4709#issuecomment-2798893841)). "Feels too ad-hoc, you can use `HttpClient.withScope` to control the lifecycle of a request explicitely" ([effect-smol#2477](https://github.com/Effect-TS/effect-smol/pull/2477#issuecomment-4827304387)). "indeed packing up different behaviour in the same function is confusing" ([effect-smol#701](https://github.com/Effect-TS/effect-smol/pull/701#issuecomment-3907787807)).
5. **Effect code is production code, not happy-path code.** "Effect is verbose is an argument that makes no sense, it is verbose compared to code that only cares about the happy path, that is not testable and doesn’t integrate telemetry. Compared to production grade code Effect is terse." ([X, 2026-08-20](https://x.com/MichaelArnaldi/status/2090355608335573400)). "Effect does not magically make your product stable, it simply gives you the tools to make it stable in a much simpler way" ([X, 2026-07-23](https://x.com/MichaelArnaldi/status/2080325967914959332)).
6. **Review everything, at the speed you can review.** "Never ship at speeds greater than what you can review." ([X, 2026-07-31](https://x.com/MichaelArnaldi/status/2083111275811180692)). "I do in fact review everything and can easily read Effect code" ([X, 2026-10-05](https://x.com/MichaelArnaldi/status/2107160704004530494)).

## Review checklist (what he checks or pushes back on)

1. **Where is the effect run?**
   - "in a normal program you should have a single run at the top which is a `runMain` not a `runSync`" ([effect#4291](https://github.com/Effect-TS/effect/issues/4291#issuecomment-2603600483)).
   - On logging a failure with `runPromise`: "Using runPromise is a loss way of handling the log, if you want proper logging you should use `Effect.catchAllCause(Effect.log)`" ([effect#5340](https://github.com/Effect-TS/effect/issues/5340#issuecomment-3172250498)).
   - "`Effect.provide` already supports `ManagedRuntime`" ([effect#5495](https://github.com/Effect-TS/effect/pull/5495#issuecomment-3284914532)).
   - Docs: "`runMain` from the platform packages is still the recommended way to run Effect programs" (signal handling, exit code, error report) ([fiber-keep-alive.md](https://github.com/Effect-TS/effect/blob/main/migration/fiber-keep-alive.md)).
   - Docs: `ManagedRuntime` "Runs many effects against services built once from a `Layer`." ([ManagedRuntime.ts](https://github.com/Effect-TS/effect/blob/main/packages/effect/src/ManagedRuntime.ts)).
2. **How many times is `Effect.provide` called, and does the service leak?**
   - "namely leaking services on usage and multiple Effect.provide calls" ([effect#5202](https://github.com/Effect-TS/effect/issues/5202#issuecomment-3094379094)). His fix composes `Inc2.Default.pipe(Layer.provideMerge(Inc1.Default))` and provides it once.
   - Docs (v4): "composing layers before providing is still the recommended pattern" and "Sibling `Effect.provide` calls therefore build their own copies" ([layer-memoization.md](https://github.com/Effect-TS/effect/blob/main/migration/layer-memoization.md)).
   - Docs (v4): "Prefer `yield*` over `use` in most cases." because `use` "makes it easy to accidentally leak service dependencies into return values" ([services.md](https://github.com/Effect-TS/effect/blob/main/migration/services.md)).
   - A batched callback gets its services from a service constructor, not from `Effect.provide` inside the callback. The user code had `Effect.provide(Database.layer)` and `Layer.orDie` inside `RequestResolver.fromEffect`. His answer: "The new RequestResolver doesn't have `R` and `E` anymore, the reason is that the context is now fully separated and batching can happen across unrelated call sites, the way to model the same would be:" a service whose `make` does `const sql = yield* SqlClient.SqlClient` and builds the resolver, with `static layer = Layer.effect(this, this.make).pipe(Layer.provide(Database.layer))` ([effect-smol#1290](https://github.com/Effect-TS/effect-smol/issues/1290#issuecomment-3921759138)). His reply kept the user's top-level `Effect.runPromise(...)`: a repro needs no `runMain`.
3. **Is a function that returns a layer called more than once?**
   - "At the moment the rule for functions returning layers is that to have a stable instance you need to extract the function call into a stable reference, which is what we do for anything like `OpenAi.layerConfig` etc" ([effect#4911](https://github.com/Effect-TS/effect/pull/4911#issuecomment-2900923499)).
   - "I would not try to do memoization, that should be left to the user if they want to." (same comment).
4. **Is a layer generic?**
   - "layers cannot be generic so accepting a schema in the base layer would not have any effect" and "You basically need to create your own specific service that identifies the drizzle instance with the schema" ([effect#4874](https://github.com/Effect-TS/effect/issues/4874#issuecomment-3106110492)).
   - "Adding a schema to the layer would not work, the types need to be tracked both on consumption and provision." ([effect#5414](https://github.com/Effect-TS/effect/issues/5414#issuecomment-3216716673)).
   - "Generally the solution of having a generic layer has been discarded in the past." ([effect#5468](https://github.com/Effect-TS/effect/pull/5468#issuecomment-3263881041)).
5. **Is a `Scope` needed here, and who owns it?**
   - "btw using `Effect.scoped` together with `Effect.provide` is usually a mistake, you shouldn't need a Scope" ([effect#5499](https://github.com/Effect-TS/effect/issues/5499#issuecomment-3286922404)).
   - "Named scopes are for locally erased resources, like the HttpConnection on a fetch call, not for resources in general, you wouldn't see many explicit scopes in a user project" ([effect-smol#49](https://github.com/Effect-TS/effect-smol/pull/49#issuecomment-2701704090)).
   - "Two independent scopes won't link in any way, that is if resources acquired in one are dependent on the other there will be issues when closing as one closes independently from the other." ([effect-smol#49](https://github.com/Effect-TS/effect-smol/pull/49#discussion_r1981920251)).
   - "the key issue is that two different scopes will close independently and resources allocated in one and the other may be interdependent, leading to potential incorrect closing order" ([effect-smol#49](https://github.com/Effect-TS/effect-smol/pull/49#issuecomment-2711093427)). He then closed the PR: "after a lot of testing I do agree with @tim-smart and @IMax153 on explicit scope" ([effect-smol#49](https://github.com/Effect-TS/effect-smol/pull/49#issuecomment-2721007069)).
   - His fix for one request: `HttpClient.withScope(yield* HttpClient.HttpClient)` and `Effect.scoped(client.execute(...))` ([effect-smol#2477](https://github.com/Effect-TS/effect-smol/pull/2477#issuecomment-4827304387)).
6. **Is a forked fiber owned, and does a background loop die silently?**
   - On `Effect.forkScoped(Effect.forever(Queue.take(queue).pipe(Effect.flatMap(send))).pipe(Effect.orDie))`: "Not sure if this repo uses Effect logging or not but if so the best would be: `.pipe(Effect.ignoreCause({ log: true }))`" ([t3code#488](https://github.com/pingdotgg/t3code/pull/488#discussion_r2901610241)).
   - His idiomatic listener: `Stream.fromEventListener(...).pipe(Stream.changesWith(...), Stream.runForEach(...), Effect.forkScoped)` ([effect#6351](https://github.com/Effect-TS/effect/issues/6351#issuecomment-5060673156)).
   - Docs (v4): "A `forkChild` fiber is interrupted when its parent exits; a `forkDetach` fiber is independent of the parent's lifetime." ([forking.md](https://github.com/Effect-TS/effect/blob/main/migration/forking.md)).
   - **Interruption** (older items, 2024, filled for the gap; the semantics did not change in v4):
     - A fork that must finish after its stream ends is joined: "that's because the stream ends, a value is returned, if you want that behaviour you should not exit and join the forked fiber" ([effect#3187](https://github.com/Effect-TS/effect/issues/3187#issuecomment-2211801529), 2024-07-06).
     - A sync loop cannot be interrupted: "The stream is fully synchronous and there is no chance of interrupting a sync op" ([effect#3141](https://github.com/Effect-TS/effect/issues/3141#issuecomment-2206870504), 2024-07-03). His fix adds `Effect.sleep` or `Effect.yieldNow` to the loop.
     - A finalizer per fiber on a long-lived scope keeps every fiber alive. Another user wrote that with `Scope.addFinalizer(scope, Fiber.interrupt(fiber))` "the Fibers will be unable to be garbage collected due to being kept within the open Scope". He agreed: "you're right, I will investigate if adding an api to remove a finaliser may be useful" ([effect#1896](https://github.com/Effect-TS/effect/pull/1896#issuecomment-1888044982), 2024-01-11).
     - Interrupt debugging: "it tells you where the program stopped and not who stopped it" ([effect#3578](https://github.com/Effect-TS/effect/pull/3578#issuecomment-2339840656), 2024-09-10).
     - His PR effect#8652 (body agent-written): "Preserve the interruption and defects, and strip typed failures when skipping those handlers" ([effect#8652](https://github.com/Effect-TS/effect/pull/8652), 2026-10-01). A pending interrupt must not be lost behind an uninterruptible region that fails.
7. **Effect or Stream?**

## Heuristics that generalize (incl. TypeScript web apps)

- One composed app layer. One `runMain` or one `ManagedRuntime` per process. In a framework with many entry points (Next.js route handlers, Workers `fetch`), the entry point calls the shared runtime, and the layer is built once. (Inference, from items 1 to 3 above.)
- A function that returns a layer is a factory. Call it once at module level and share the value. (From [effect#4911](https://github.com/Effect-TS/effect/pull/4911#issuecomment-2900923499).)
- A service with a type parameter is a new specific service, not a generic layer. (From [effect#4874](https://github.com/Effect-TS/effect/issues/4874#issuecomment-3106110492).)
- Resources need the smallest scope that fits their life. Most app code needs no explicit `Scope`. (From [effect-smol#49](https://github.com/Effect-TS/effect-smol/pull/49#issuecomment-2701704090) and [effect#5499](https://github.com/Effect-TS/effect/issues/5499#issuecomment-3286922404).)
- Read request-local values (cookies, headers, auth from `AsyncLocalStorage`) at the edge and pass them in as a service. (From the 3.20 advisory.)
