# Armin Ronacher (@mitsuhiko): code-review research

Research date: 2026-11-26. Weighting: 2025 to Nov 2026 highest.
Main corpus: 803 of his GitHub comments in 435 threads, 2025-01-05 to 2026-11-25 (found with `commenter:mitsuhiko` and `reviewed-by:mitsuhiko`, then filtered by `user.login`). Most are in `earendil-works/pi`, `mitsuhiko/minijinja`, `earendil-works/gondolin`, `earendil-works/absurd`, and `mitsuhiko/similar`. Other sources: 43 of his blog posts (2016 to 2026, most from 2025 and 2026), his committed code-review prompt for Pi (`/review`), 263 of his X posts (2026-09-15 to 2026-11-25, 16 timeline pages), 462 of his Bluesky posts (2024-12-26 to 2026-11-24), a 2020 HackerNoon interview, and the published notes of two Pragmatic Engineer episodes.
Second pass (2026-11-26): 217 of his Hacker News comments (`the_mitsuhiko`, 2025-11-27 to 2026-11-26), 733 of his X posts (2026-06-10 to 2026-11-25, 43 timeline pages, which fills the X gap back to June), and his comments on 109 pull requests by other authors that were opened after 2025-11-26 (search `is:pr commenter:mitsuhiko -author:mitsuhiko` and `reviewed-by:mitsuhiko`). Of those 109 pull requests, only 12 have line comments or review bodies from him in a human voice. This pass also replayed 5 of his reviews against the seat (see "Replay").
Every quote is verbatim. I kept his typos ("shuold", "no such things as user error") and his double spaces after a full stop. A script checked each quote against the fetched text. "Inference" marks my own reading. "Paraphrase" marks text that I did not quote.

**Important: some of his GitHub comments are written by an agent.** 63 of the 803 comments say so ("This comment is AI-generated by `/wr`", "written by an AI assistant (Claude) on behalf of @mitsuhiko"). Some longer reviews in `minijinja` have no label but read like agent output (test matrices, "3,792 cases"). This file quotes human-voice comments for his opinions. It marks every agent-written quote with "(agent-written)".

**He rarely does line-by-line review.** Only 15 review bodies and 14 inline comments are in the corpus. The second pass confirms it: in the last year, pi#6064 is the only pull request by someone else where he left more than two line comments. His usual moves are: one short comment with the alternative, close the PR, or rebuild a smaller version on `main` and close the PR as superseded.

## Core values

1. **Fail loudly. Do not swallow errors.** "It loves to swallow errors and take away all tracebacks. I’d rather uphold strong invariants and let code crash loudly when they fail, than hide problems. If you don’t fight this, you end up with opaque, unobservable systems." ([90%, 2025-09-29](https://lucumr.pocoo.org/2025/9/29/90-percent/)). His review prompt: "Prefer propagation over local recovery." and "When uncertain, prefer crashing fast over silent degradation." ([commit 401fa86](https://github.com/mitsuhiko/agent-stuff/commit/401fa86442c77f446a9c91e51f88f87517f8f671)). In Pi: "We currently intentionally crash when extensions misbehave to make it easier to debug broken extensions." ([pi#5597](https://github.com/earendil-works/pi/issues/5597#issuecomment-4693016751)) and "The PR in question removes the crash handling which is not at all what we want." ([pi#4946](https://github.com/earendil-works/pi/issues/4946#issuecomment-4527872689)).
2. **Make the bad state impossible. Do not tolerate it.** "Almost always, the correct fix is not to handle the bad state, but to make the bad state impossible." ([Building Pi With Pi](https://lucumr.pocoo.org/2026/5/24/pi-oss/)). "The right fix is to make the malformed case unrepresentable or impossible to write in the first place." ([The Coming Loop, 2026-06-23](https://lucumr.pocoo.org/2026/6/23/the-coming-loop/)). His review prompt: "Flag defensive checks or fallback behavior that mask programming errors, especially when callers already guarantee the relevant invariants." ([commit f1de050](https://github.com/earendil-works/pi-review/commit/f1de050504936046c0f85b21fec0e0a93ef394eb)).
3. **Design errors like return values.** "you should spend the same amount of time designing the error types as the return values. You cannot have enough contextual information on errors." and "There is a shocking amount of code that just writes error messages into an exception and calls it a day." He calls the result "stringly typed error handling" ([HackerNoon interview, 2020](https://hackernoon.com/interview-flask-creator-armin-ronacher-yx3r3wzs)). In 2026 he put it in his review prompt: "Ensure that errors are always checked against codes or stable identifiers, never error messages." ([commit 3e69266](https://github.com/mitsuhiko/agent-stuff/commit/3e692669366f837c9f8e3bd8f3bc4e691255c5c9)). Also: "Good error reporting: a compiler, tool or an API that does not provide good error reporting is a bad tool." ([We Can Just Measure Things, 2025](https://lucumr.pocoo.org/2025/6/17/measuring/)).
4. **Every public API is a maintenance promise.** "I'm not entirely opposed but it's a new API we would need to keep stable, and I'm not entirely convinced that we should." ([pi#5755](https://github.com/earendil-works/pi/issues/5755#issuecomment-4705776592)). "I don't know to which degree I want to expose too much from the SDK because the goal is for it to be lightweight and every API added is one more thing to maintain." ([absurd#21](https://github.com/earendil-works/absurd/issues/21#issuecomment-3480447397)). Libraries and apps differ: "reusability is not that important when you’re building an application, but it’s crucial when you’re building a library or framework." ([Ugly Code and Dumb Things, 2025](https://lucumr.pocoo.org/2025/2/20/ugly-code/)).
5. **Fix the cause where it lives: upstream, or in your own API. Do not pile up local hacks.** "Many times the right answer is not to work around a problem locally, but to make the upstream behavior correct." ([Building Pi With Pi](https://lucumr.pocoo.org/2026/5/24/pi-oss/)). "I think given this behavior the actual fix is upstream within OpenCode Zen instead of throwing more hacks into Pi.  I don't think what Pi is doing here is wrong." ([pi#4251](https://github.com/earendil-works/pi/issues/4251#issuecomment-4468426603)). "I will fix this differently by fixing the API." ([gondolin#14](https://github.com/earendil-works/gondolin/pull/14#issuecomment-3867006137)).
6. **Code must be readable locally: few layers, one import path, no hidden checks.** "Few superfluous abstractions: too many layers just make data flow and refactoring expensive." ([Measure Things](https://lucumr.pocoo.org/2025/6/17/measuring/)). "agents really like local reasoning." and "A one-to-one mapping from where something is declared to where it’s imported from is great." ([A Language For Agents, 2026-02-09](https://lucumr.pocoo.org/2026/2/9/a-language-for-agents/)). "Keep important checks local." ([Agentic Coding Recommendations, 2025](https://lucumr.pocoo.org/2025/6/12/agentic-coding/)).
7. **Agent-written code is your code. You own every line and every word.** "I still treat every line as my responsibility, judged as if I wrote it myself." ([90%](https://lucumr.pocoo.org/2025/9/29/90-percent/)). "They will recreate things that already exist. They create abstractions that are completely inappropriate for the scale of the problem." (same post). "Present-day models tend to produce code that is too defensive, too complex, too local in its reasoning. They avoid strong invariants. They add fallbacks instead of making bad states impossible. They duplicate code, invent bad abstractions, and paper over unclear design with more machinery." ([The Coming Loop](https://lucumr.pocoo.org/2026/6/23/the-coming-loop/)).
8. **Bounded flow. Overload is an error, not a buffer.** "It’s in fact better to admit defeat — that you’re overloaded — than to pretend that you’re operational and keep buffering up forever because at one point it will only make matters worse." ([I’m not feeling the async pressure, 2020](https://lucumr.pocoo.org/2020/1/1/async-pressure/)). His review prompt: "Treat back pressure handling as critical to system stability." ([commit 401fa86](https://github.com/mitsuhiko/agent-stuff/commit/401fa86442c77f446a9c91e51f88f87517f8f671)). In Pi: "If that is the case, the actual problem is that we're not handling backpressure correctly, not that we're not hooking up the `error` event." ([pi#4897](https://github.com/earendil-works/pi/issues/4897#issuecomment-4527884378)).

## Review checklist (what he checks or pushes back on)

1. **Does a catch hide a failure?**
   - His review prompt: "Flag catch blocks that hide failure signals (e.g. returning" null, empty array, or false, "swallowing JSON parse failures, logging-and-continue, or “best effort” silent recovery)." ([commit 401fa86](https://github.com/mitsuhiko/agent-stuff/commit/401fa86442c77f446a9c91e51f88f87517f8f671))
   - "Boundary handlers (HTTP routes, CLI entrypoints, supervisors) may translate errors, but must not pretend success or silently degrade." ([commit 401fa86](https://github.com/mitsuhiko/agent-stuff/commit/401fa86442c77f446a9c91e51f88f87517f8f671))
   - "If a catch exists only to satisfy lint/style without real handling, treat it as a bug." ([commit 401fa86](https://github.com/mitsuhiko/agent-stuff/commit/401fa86442c77f446a9c91e51f88f87517f8f671))
   - On agents: "agents will try to catch everything they can, log it, and do a pretty poor recovery." ([A Language For Agents](https://lucumr.pocoo.org/2026/2/9/a-language-for-agents/))
2. **Does the change tolerate bad data that the system itself writes?** "If you tell them that “this malformed session log crashes the reader,” the clanker will often add a tolerant reader. Then it will add a fallback, then maybe a migration, then more debug output, then a test for all of this." and "All these models see a local failure and try to locally defend against it. As maintainers we have to keep pulling the conversation back to the global invariant, which is harder than it should be, and it’s laborious." ([Building Pi With Pi](https://lucumr.pocoo.org/2026/5/24/pi-oss/))
3. **Can a caller branch on the error without reading its message?**
   - "Ensure that errors are always checked against codes or stable identifiers, never error messages." ([commit 3e69266](https://github.com/mitsuhiko/agent-stuff/commit/3e692669366f837c9f8e3bd8f3bc4e691255c5c9))
   - On an error message in Pi: "I wonder if it wouldn't be better to just report `Could not write file: ${path} (error ${error.code})`." ([pi#3955](https://github.com/earendil-works/pi/pull/3955#issuecomment-4345249730))
   - In Deser: "Errors are something I care a lot about" and the goal is "errors that point at the problem" ([Deser, 2026-09-29](https://lucumr.pocoo.org/2026/9/29/deser/)). In minijinja-cli: "Also it now reports undefined errors correctly with location info." ([Bluesky](https://bsky.app/profile/mitsuhiko.at/post/3lgshw3txtc2p))
4. **Will the error show up where people look?** "It also means errors should be where they can be found. If errors are hidden in an obscure log neither human nor agent will find it." ([Measure Things](https://lucumr.pocoo.org/2025/6/17/measuring/)). From the lock-poisoning cases: "the original panic could not even be found in the logs." ([Abolish Lock Poisoning, 2026-11-25](https://lucumr.pocoo.org/2026/11/25/poisoning/))
5. **Does one failure turn into permanent failure?** "Deviously poisoning does not fail fast and done wrong, it fails forever." and "When a panic happens with a lock held, there are two reasonable reactions: shut the process down, or carry on and ignore the flag." ([Abolish Lock Poisoning](https://lucumr.pocoo.org/2026/11/25/poisoning/)). Also: "Primarily this is because I have yet to come across code in the wild that handles a poisoned lock correctly." (same post). Inference: an error-recovery path that nobody handles correctly should not exist.
6. **Is this a new public API? Must it stay stable?**
   - "I'm not entirely opposed but it's a new API we would need to keep stable, and I'm not entirely convinced that we should." ([pi#5755](https://github.com/earendil-works/pi/issues/5755#issuecomment-4705776592))
   - "I don't think I want to make that functionality part of the regular API." ([absurd#29](https://github.com/earendil-works/absurd/issues/29#issuecomment-3527887580))
   - His review prompt has a required callout: "This change introduces backwards-incompatible public schema/API/contract changes" ([review.ts](https://github.com/earendil-works/pi-review/blob/main/review.ts)).
7. **Does the API offer something it cannot do?**
   - "But yes, it would be better if the entire instant system was just not there if it cannot be provided." and "maybe this is the moment to clean up this entirely and take away the deadline functions if they cannot be provided." ([similar#76](https://github.com/mitsuhiko/similar/pull/76#issuecomment-2637919495))
   - "The JS binding does not expose a custom formatter, so this advertised mode cannot actually render and currently just errors." and "Please update `minijinja-js/README.md`, which still lists custom auto-escape callbacks as unsupported." ([minijinja#902](https://github.com/mitsuhiko/minijinja/pull/902#pullrequestreview-4843863651), no AI label, possibly agent-assisted)
   - In minijinja-js, the same review asks to "restrict the return values to the supported modes" instead of keeping a mode that "cannot actually render and currently just errors" ([minijinja#902](https://github.com/mitsuhiko/minijinja/pull/902#pullrequestreview-4843863651)).
   - Types must say what the function returns: "The return value should be changed to `*mut c_char` then." ([minijinja#754](https://github.com/mitsuhiko/minijinja/pull/754#issuecomment-2734883332))
8. **Does the API make misuse easy?** On Python's stream writer: "Well it’s a massive API oversight and I’m not exactly sure how it happened." ([async pressure](https://lucumr.pocoo.org/2020/1/1/async-pressure/)). "CVE-2024-12254 Is a good reminder that the python async write API is bad design. Even in the stdlib people forget to drain." ([Bluesky](https://bsky.app/profile/mitsuhiko.at/post/3lgvrgcpcws24)). His fix in Gondolin is to change the API shape: "Basically I want to directly pass to `exec()` what is supposed to happen with the data (buffer, forward to a stream).  Since you cannot exert back pressure with how this works today, the API is probably always going to be a bit different." ([gondolin#13](https://github.com/earendil-works/gondolin/issues/13#issuecomment-3867037465))
9. **Does a loose input contract teach callers to be sloppy?** About Claude Code's tool handling: "Anthropic’s own client appears to expect and accept a fair amount of slop and repairs it, mostly silently." and "The harness fully absorbs the error and there is little gradient against inventing an alias, adding a stray field or using a nearby parameter name." His conclusion: "then the harness needs stronger guarantees somewhere." ([Better Models: Worse Tools, 2026-07-04](https://lucumr.pocoo.org/2026/7/4/better-models-worse-tools/))
10. **Is this a local hack for someone else's bug?**
    - "My appetite to work around bugs in pi for issues upstream is rather low.  There are too many messes out there to deal with." ([pi#5718](https://github.com/earendil-works/pi/issues/5718#issuecomment-4702805312))
    - "Not going to put hacks into pi for old macos bugs." ([pi#5667](https://github.com/earendil-works/pi/issues/5667#issuecomment-4693277054))
    - "The issue here is that really an upstream provider should not give us bad data.  Pi currently tries to keep hacks within the message handling to a minimum" ([pi#5921](https://github.com/earendil-works/pi/issues/5921#issuecomment-4759080788))
    - "is slop and I don't want to have that pattern spread.  Should be fixed properly." ([pi#12206](https://github.com/earendil-works/pi/issues/12206#issuecomment-7041497761))
11. **Two code paths for one job?** "I feel not very confident in supporting both code paths.  I think the better option would be to evaluate moving to typebox 1.0 and using the validation from there instead of AJV.  Then at least the whole thing is consistent." ([pi#3112](https://github.com/earendil-works/pi/issues/3112#issuecomment-4258604353))
12. **Does it copy a standard? Then match it.**
    - "While appealing, that filter does not have that behavior in Jinja2 and I'm not sure it's a great idea to diverge from there." ([minijinja#827](https://github.com/mitsuhiko/minijinja/pull/827#issuecomment-3217448058))
    - "the goal is npm parity. what does npm do for tarball publishes? My pushback was your over-engineering for multiple competing readme files." ([bun#30257](https://github.com/oven-sh/bun/pull/30257#discussion_r3187724317))
    - "I want to stay in line with standard ghostty behavior." ([pi#7733](https://github.com/earendil-works/pi/pull/7733#issuecomment-5208837907))
13. **Does it add a protocol or mode to the core when an edge adapter would do?** "I think it's a bit unfortunate if this ends up with many different protocol versions in the core server because it will be tricky to support them all at the same level of quality without blowing up the complexity. I wonder if it would not be better to have a separate proxy that translates to one common protocol." ([antirez/ds4#91](https://github.com/antirez/ds4/pull/91#issuecomment-4435105068)). Also: "I would encourage people not to design an overly complex negotiation protocol just because someone else saw the need in some other system like SignalR." ([MCP#206](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/206#discussion_r1999325642))
14. **Is the fix right but too big?**
    - "The fix is right, but also quite excessive so I want to see what other, better options might exist." ([absurd#61](https://github.com/earendil-works/absurd/pull/61#issuecomment-3684300206))
    - "Going to close this for the complexity of all of it.  First we need a clear understanding how to reproduce this and an issue report." ([pi#6266](https://github.com/earendil-works/pi/pull/6266#issuecomment-4873567451))
    - "I like the feature but the implementation was more than it needs to be, so I rebuilt it minimally on main rather than merging this as-is." ([pi#9080](https://github.com/earendil-works/pi/pull/9080#issuecomment-5532010118), agent-written)
15. **Does it already exist?** "I feel like this shuold be a thing we already have somewhere reused?" ([gondolin#120](https://github.com/earendil-works/gondolin/pull/120#discussion_r3519232050)). His review prompt: "Check whether each newly added function duplicates existing functionality elsewhere in the codebase." and "Flag one-off helper functions that add indirection without improving clarity or reuse" ([commit f1de050](https://github.com/earendil-works/pi-review/commit/f1de050504936046c0f85b21fec0e0a93ef394eb)).
16. **Is the AI diagnosis verified?** Pi's issue prompt says: "Do not trust analysis written in the issue. Independently verify behavior and derive your own analysis from the code and execution path." and "A bad issue that contains a plausible but wrong diagnosis creates extra work." ([Building Pi With Pi](https://lucumr.pocoo.org/2026/5/24/pi-oss/)). On a report: "It makes debugging and resolving such issues harder because now when I point a clanker at this issue it already goes down a completely inaccurate path." ([pi#4897](https://github.com/earendil-works/pi/issues/4897#issuecomment-4527964560))
17. **Is a guard, timeout, or crash intentional?** Read why it exists before removing it: "It was intentionally set to 10 seconds because otherwise you wait for the retry 5 minutes which is the default.  Putting this to 5 minutes regresses for APAC uses on what this thing is supposed to fix." ([pi#5600](https://github.com/earendil-works/pi/pull/5600#issuecomment-4691952418)). But when the reason is gone, remove it: "It was intentional, but the original reason for why it behaved this way is gone now." ([minijinja#777](https://github.com/mitsuhiko/minijinja/issues/777#issuecomment-2838212639))
18. **Does the API promise enough for its callers?** On a token getter: "`modelRuntime.getAuth` ideally should ensure that the token it gives out is valid for at least 30 minutes (I think it should be able to guarantee that)." 19. **Does a name describe the behavior, not the history?** "I think this is fine, but I don't think we should call the other mode `legacy`.  Ideally we just call it `shared` and `unique` or something and we explain the differences." ([gondolin#123](https://github.com/earendil-works/gondolin/pull/123#issuecomment-4884089707))
20. **Is the intent visible to a reviewer?** "You could accidentally land a change that makes the optimization impossible and it would not be found in code review.  Adding annotations not just helps the optimizer, but also the compiler and the user." ([rust-lang/rfcs#3720](https://github.com/rust-lang/rfcs/pull/3720#discussion_r2015974487))
21. **Does a port match the client it copies?** When a flow copies a reference client, he compares behavior case by case, down to status codes and edge values.
    - "codex also treats 403 and 404 as pending" ([pi#4911](https://github.com/earendil-works/pi/pull/4911#discussion_r3309222327))
    - "`<= 0` should be `< 0`." ([pi#4911](https://github.com/earendil-works/pi/pull/4911#discussion_r3309228390)). Inference: the interval check rejected 0, a value the reference accepts.
    - "I think we should do this and the code looks fine, but last time I intentionally did not implement it because codex did not do, and seemingly it does not do yet either." ([pi#6955](https://github.com/earendil-works/pi/pull/6955#pullrequestreview-4753498533))
    - "we look at what the models are doing.  They are trained on their respective harnesses and we're not here to fight their behavior." ([HN 49926377](https://news.ycombinator.com/item?id=49926377))
22. **Does the published package run, and is its metadata true?** On a new package in the Pi monorepo:
    - On a CLI path that resolves only inside the monorepo: "This won't work for actual pi builds.  We will need something better there.  Also we will run into issues with bun here." ([pi#6064](https://github.com/earendil-works/pi/pull/6064#discussion_r3474094662))

    - On a `repository` URL that points to the old repo: "Woops?" ([pi#6064](https://github.com/earendil-works/pi/pull/6064#discussion_r3474116841))
23. **Does a start in several steps clean up after a failure?** "Then track acquired resources separately: `rpcProcess?: started`, `radiusPiId?: registered`, `sessionId?: synced`, so cleanup can run in reverse order regardless of where a transition failed." and "On any failure, move to `error` or `stopped` after best-effort cleanup of whatever was acquired." ([pi#6064](https://github.com/earendil-works/pi/pull/6064#discussion_r3474115762)). Lane note: the state machine itself is lifecycle (Mitchell seat). The downside is that now observers can get a `NULL` payload." ([absurd#61](https://github.com/earendil-works/absurd/pull/61#issuecomment-3684423882)). Lane note: size of the fix goes to the Blow seat.

## What he praises

- **Thin SDKs over a simple core.** "Putting the complexity in SQL and keeping the SDKs thin turned out to be a genuinely good call." and "When something goes wrong, you can read the entire SDK in an afternoon and understand what it does." ([Absurd In Production, 2026-04-04](https://lucumr.pocoo.org/2026/4/4/absurd-in-production/)). Also: "I generally try to avoid bringing in extra complexity if I can avoid it" ([Absurd Workflows, 2025](https://lucumr.pocoo.org/2025/11/3/absurd-workflows/)).
- **Plain data and functions.** "My codebase so far is basically: dataclasses and functions that transform/insert/update them in the DB. Raw SQL and some database query helpers. Turns out LLMs love that. What's great for humans is also great for agents." ([Bluesky, 2025-05-28](https://bsky.app/profile/mitsuhiko.at/post/3lqatcg57lk2q)). "Prefer functions with clear, descriptive and longer than usual function names over classes." ([Agentic Coding Recommendations](https://lucumr.pocoo.org/2025/6/12/agentic-coding/))
- **Shallow abstractions.** About a messy forum that shipped: "The abstractions were one layer deep." ([Ugly Code](https://lucumr.pocoo.org/2025/2/20/ugly-code/))
- **Deleting code.** "Latest best feature of Agentic coding for me is how good they are at removing code." ([Bluesky, 2025-07-21](https://bsky.app/profile/mitsuhiko.at/post/3luhu6wkifk2l)). He also removes migrations: "The solution here is to eventually remove the migration." ([pi#5661](https://github.com/earendil-works/pi/issues/5661#issuecomment-4693556391))

## Heuristics that generalize (incl. TypeScript web apps)

Each item names its source. The translation to TypeScript web apps is my inference.

1. **No silent catch.** Flag `catch {}`, `catch (e) { console.error(e) }` followed by normal flow, `.catch(() => null)`, `?? []` after a failed fetch, and `try { JSON.parse(x) } catch { return {} }`. Catch only in a route handler, a server action boundary, a queue consumer, or a CLI entry, and there return a real error response. In Effect, `Effect.orElse`, `catchAll`, or `orDie` that turn a typed failure into a default value get the same check. (review prompt; 90% post)
2. **Errors carry a code and context.** A thrown or returned error names the operation and the ids (`user`, `path`, `status`) and keeps `{ cause }`. Callers branch on `error.code`, a tagged union, or an Effect tagged error, never on `error.message.includes(...)`. HTTP APIs return a stable machine-readable error code next to the message. (HackerNoon; review prompt; pi#3955)
3. **Validate on write. Do not repair on read.** For rows, JSON columns, localStorage, KV, and queue messages that the app writes itself, validate before the write (schema, DB constraint) and let a bad read fail loudly. Do not add a lenient parser, a `migrateIfOld()` path, or a "repair" step. Parse untrusted input once at the boundary into a strict type. (Building Pi With Pi; The Coming Loop)
4. **One failure must not poison the process.** In Workers and server modules, a module-level cached promise that rejected once (`let client = createClient()`) fails every later request. Clear it on failure, or let the isolate crash. (Abolish Lock Poisoning, inference)
5. **Count the exports.** Each new `export` from a package entry, each new API route, each new field in a response, webhook, or event payload, and each new SDK method is a promise. Ask who calls it. If nobody outside the module does, do not export it. (pi#5755; absurd#21)
6. **One import path per symbol.** No barrel `index.ts` that re-exports a folder, no `export * from`, no import aliases for the same module. (A Language For Agents)
7. **Do not advertise what does not work.** Remove an option, mode, prop, or endpoint that only throws a not-supported error. Keep README and types true. (similar#76; minijinja#902)
8. **Strict contracts at your boundary.** Use strict schemas for your HTTP API, tool definitions, and webhooks, and reject unknown or wrong fields with a clear error. Silent coercion and alias fields teach callers to send bad data. (Better Models: Worse Tools)
9. **Upstream bug: report it, then keep the workaround small and at the edge.** A workaround for Supabase, a browser, an LLM provider, or a library bug gets a comment with the upstream issue link and the version, and stays in one adapter, not across the app. If the bug is in your own API, change the API instead. (pi#4251; pi#5718; gondolin#14)
10. **Match the standard you copy.** A wrapper around `fetch`, `Request`, `Response`, `URL`, cookies, or an upstream SDK keeps the standard behavior and lists each known difference. (minijinja#827; bun#30257)
11. **Bound every flow.** Queues, in-memory arrays that grow per request, streams, retries, and fan-out need a limit, a timeout, and a clear overload error. A stream writer respects backpressure (`await writer.ready`, `pipeTo`). (async pressure; review prompt; pi#4897)
12. **Errors go where people look.** Log once at the boundary with context, to the place the team reads (Sentry, Workers logs, Supabase logs). Do not log and continue deep inside. (Measure Things)
13. **Keep checks local.** Authorization stays next to the route or query that needs it, not in a far config. (Agentic Coding Recommendations) Security depth goes to the security seat.
14. **App code may be plain. Library code must be stable.** Do not ask an app to be reusable. Do ask a shared package or SDK for a small, stable surface. (Ugly Code)
15. **Agent diff check.** For an agent-written diff, look for: a duplicate of an existing helper, a new abstraction with one use, a fallback for an invariant, a catch that logs, a long PR description. (90%; The Coming Loop; review prompt; pi#4463)
