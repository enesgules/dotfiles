# Draft an X post

Write posts that a stranger stops for, reads to the end, and wants to quote. Hand the user text they can copy. Do not publish, reply, or schedule: posting is their call, and their name is on it.

## 0. Know the author

A post sounds right only when it sounds like the person who posts it. Before you write, find out:

- who they are and what they build (product, role, company)
- who reads them (for example, frontend devs, AI tool builders, indie hackers)
- the language they post in

Look in the conversation, project files, and any memory or profile notes first. Ask only for what is still missing, in one short question. Use these facts to pick the angle and the voice. Put a personal fact in the post only when the user wants it there.

Write in the language of the request. Keep product names as the user writes them. Translate only when asked.

## 1. Topic and goal

Every post needs one topic and one goal. Pick the goal:

- **Value.** A short guide the reader can use today.
- **Build in public.** One public goal, and the messy work toward it.
- **Launch.** A product, feature, or repo that is ready to show.
- **Thread.** A how-to that starts from an objection.

State the topic and goal in one line. If you inferred either, say so. If you cannot infer the goal, ask once, name the four goals, and stop.

Collect the facts the post stands on: what changed, a before and an after or output, a link, and any number, price, or comparison the user wants public. For a launch, ask whether it is open source. If the user pastes someone else's post to remix, keep the hook idea and write new lines. Do not copy sentences.

## 2. Pick the format

Use one format for every variant, so the user compares hooks, not structures.

**Value.** The first line is the result a stranger gets. Then a short list or a few numbers. No block of prose. It gives a benefit; it is not a diary.

**Build in public.** Name the one goal. Show today's step, what happened, and the next step. People follow the story of a goal, so the goal must be clear in every post. Add a real result only if the user gave one.

**Launch.** Use this shape. Keep the price line, the open-source line, and each proof bullet only when the user gave that fact. Three bullets need three facts; if there are fewer, ask. A bullet filled with an adjective reads as an ad.

```
Introducing {name}

{price or scope against the usual alternative}

- {proof}
- {proof}
- {proof}

Fully open source

{link}
```

**Thread.** Open with an objection the user has heard, reject it, and promise the how-to:

```
"{objection}"

BS. Here is how.

🧵
```

Use a softer rejection when "BS" does not fit. Then one short post per real step, numbered. Do not pad: a thread with filler steps loses readers at the filler.

Under every variant, add one line: the image or short video to attach, and what it must show (the before and after, the output, the fix). On X, a post with a clear visual gets read; a wall of text gets scrolled past.

## 3. Write 2 or 3 variants

Each variant has a hook in the first line, then the value. A good hook names a problem the reader has, a result they want, or a claim they will argue with. A product name alone is not a hook, because strangers do not know the product yet.

Write like a person:

- Short lines. A list or numbers when there is more than one point.
- Plain words. Read it aloud. If it sounds like a model wrote it, rewrite it.
- A little fun. It can sound like work the author enjoys.
- One call to action at the end is enough.

Do not rant, and do not mock a group to farm replies. That gets reach once and costs trust. Avoid model words: delve, leverage, unlock, tapestry, landscape, game-changer, seamless, empower, supercharge, "excited to share", "let's dive in", "here's the thing".

A single post fits without "Show more". A launch may run a little longer to keep its proof lines. A thread is a series of short posts. Go long only when asked.

## 4. Check, then rewrite

Check each variant before you show it. Each item is pass or fail. Rewrite until all five pass; if a variant still fails after two rewrites, drop it and write a new one.

1. **Stranger.** Hide the author's name. A reader who has never heard of them still gets a step, a fix, or a result.
2. **Skim.** Short lines. A list or numbers for more than one point. No paragraph over two lines.
3. **Quote.** A specific before, output, or fix that someone can quote and add to. A launch must pass this.
4. **Proof.** Every number, price, user count, and comparison came from the user. You added none. Invented proof is the fastest way to lose credibility in the replies.
5. **Voice.** Not a rant, not rage bait, not an ad, not model prose.

If Proof or Quote fails because the user gave no concrete detail, ask for one (what changed, what it does, a number they will stand behind). Do not invent it.

Under the variants, add one line such as `Checks: A pass, B pass, C pass.`

## 5. Launch angles

For a launch, suggest 2 or 3 angles that other people can post about:

- Founder story
- What changes for the reader
- A short video reaction
- A take the author can defend (a specific claim, not an insult)
- Two groups that want different things

For each angle, name the kind of person who has lived it, what access to give them, and a one-line brief. They write it in their own words; a copied script reads as paid.

## 6. Notes under the draft

Add this short section every time.

- **Mix.** A healthy account is roughly 40% entertaining, 30% educational, 20% inspirational, 10% selling. Say which job this post does, so the user can see if they post too many ads.
- **Replies.** The author writes their own replies; AI replies are easy to spot and hurt trust. Do not draft reply text. You may list questions the post will likely get, so they can prepare.
- **What worked.** When the user says a format, angle, or topic worked, reuse it on the next draft.
- **Not landing?** Check the profile before the copy: a recognizable photo, a one-sentence bio, and a pinned post that states the one goal.
- **After posting.** Read the replies, log repeat questions and objections, post again when one is fixed, and repost the best replies with credit. Pick the next post from trials, DMs, and sales, not from views.
